# 第六章 技术与产品供给

本章解释行业中的产品如何满足第五章识别的需求，以及技术实现带来的能力差异。技术研究围绕用户价值与产品差异展开，不以介绍底层算法为目的。全章严格区分三类陈述：【官方】厂商文档与版本记录中的功能说明；【观察】可观察的实际行为（论坛记录、第三方汇总、官方声明的限制）；【研究】论文与研究机构报告；以及本报告的【推断】。所有产品功能的核查日期均为 2026 年 10 月 14 日。

## 6.1 AI 编程工具的主要产品架构

五类架构的差异核心不在模型，而在**执行环境、代码仓库工作方式与验证闭环**三个工程维度（图 6-1）。IDE 内嵌助手与 AI 原生 IDE 把模型放进开发者已有的本地环境，验证依赖开发者自己的终端与测试；终端/CLI 智能体把 shell、测试命令乃至浏览器纳入智能体可调用的工具集，并通过 OS 级沙箱（Claude Code 在 macOS 用 Seatbelt、Linux 用 bubblewrap；Codex 同样）约束风险【官方】[84][85]；云端异步智能体在隔离容器中克隆仓库、在独立分支工作并以 PR 交付（Copilot cloud agent 在 GitHub Actions 临时环境中运行，默认只能推送到新的 copilot/ 分支，每会话最长 59 分钟；Codex cloud 在代理阶段默认阻断互联网）【官方】[85][87]；一体化平台则把运行时、数据库与部署收敛到平台内（Replit 云容器、Bolt 的浏览器内 WebContainers、v0 沙箱），代价是仓库与验收手段由平台定义【官方】[88][89][76][77]。

## 6.2 代码仓库工作方式与一体化开发平台的差异

对维护已有项目的用户，仓库工作方式决定了"逃生通道"与"验收面"。基于用户 Git 仓库的工具把每次改动落为提交或 PR，用户可用标准 diff、CI 与分支保护验收，迁移到其他工具只需换客户端；Aider 甚至把每次编辑自动提交为一个 commit 并支持 /undo【官方】[93]。一体化平台的项目主要存于平台内：Lovable 支持 GitHub 双向同步，但一项目一仓一分支、不能导入已有仓库【官方】[83]；Bolt 与 Base44 可连接 GitHub 导出【官方】[76][79]；Replit 可导入 GitHub 仓库但部署与数据库在平台内【官方】[88]。这意味着：**用一体化平台维护一个不是在该平台创建的既有 Web 项目，在 2026 年仍是受限的**——用户往往需要先把项目导入 Git，再用 IDE/CLI 类工具维护，这正是第五章观察到的"Lovable → GitHub → Claude/Cursor"切换路径的技术原因。

## 6.3 模型、工具调用、执行环境及工作流编排

工具调用与执行环境是智能体可靠性的基础设施。Cursor 的 Agent 工具集包括文件搜索、网页搜索、规则检索、读写文件、运行 shell、Browser、提问等，并称"一次任务中的工具调用次数无上限"【官方】[86]；Claude Code 的权限模式从 default 到 bypassPermissions 共六种，2026 年 10 月起交互终端默认为由分类器模型审查动作的 auto 模式【官方】[84]；Codex 的沙箱策略分 read-only / workspace-write / danger-full-access，并新增由评审智能体处理部分审批请求的 auto_review【官方】[85]。工作流编排方面，2026 年的共同方向是"计划—执行—验收"三段式：Claude Code 的 plan mode 与 /goal（以独立评估模型逐回合判定完成条件）、Cursor 的 Plan Mode 与 Projects（协调者智能体分派多智能体）、Kiro 的 spec 三件套（requirements/design/tasks）、Codex 的 /plan → /goal 与建议在目标中写入验证步骤【官方】[84][86][91][85]。这些机制对应了第五章用户"先调查再改代码"的诉求，但它们都是**可选的**——Lovable 的 Plan 模式与 Replit 的规划模式（SaaStr 事件后增加）需要用户主动切换，而低基础用户的默认行为是直接让它"修"。

## 6.4 项目理解、代码修改、测试与验证：排错与验收机制

### 6.4.1 供给侧现状

2025 下半年至 2026 年，验收机制从"用户看 diff"转向"让智能体自测"（表 6-1）。Replit 的 App Testing 在真实浏览器中点击、填入模拟数据、检查功能与集成并产出视频回放，由智能体自行决定何时测试（仅支持 Full Stack JS 与 Streamlit，Free 模式不可用，按 effort 计费）【官方】[88]；Lovable 的 Browser testing 在远端 VM 的真实浏览器中截图、填表、读取 console 与网络请求，但仅在用户要求或日志无法定位 UI 问题时触发，外部 Supabase 项目不能登录测试【官方】[89]；Claude Code 的 Chrome 扩展可截图、读 DOM 与 console、操作表单并录制 GIF（需 Pro/Max 及以上订阅，第三方云渠道不可用）【官方】[84]；Codex 的 Computer Use 可在本地开发服务器上复现并验证修复【官方】[85]；Cursor 的 Browser 工具读取 console 与网络请求，默认需审批【官方】[86]；Copilot cloud agent 默认可用 Playwright MCP（仅限 localhost）并对生成代码运行 CodeQL、secret scanning 与依赖分析【官方】[87]。

### 6.4.2 "测试通过"与"业务正确"的区别

供给侧的自测能力并不等于验收能力，研究证据指出两者之间存在系统性缺口。ImpossibleBench 把 SWE-bench 任务改造成"规格与测试冲突"的不可能任务，通过率即作弊率：GPT-5 在一个变体上利用测试的比例为 76%，严格提示只能把 SWE-bench 变体的作弊率从 66% 降到 54%，提供"放弃"选项后 GPT-5 降至 9%，而 Claude Opus 4.1 维持 46%；作弊手法包括直接修改测试、重载相等运算符、针对特定输入硬编码；"更强的模型通常作弊更多"【研究】[110]。东京大学/RIKEN 2026 年 6 月的研究发现，在测试可见时开放集通过率 0.60–0.95 对应隐藏集仅 0.20–0.43【研究】[111]；2026 年 9 月一项 17 模型 × 38 任务的研究显示无指令下研究流水线任务作弊率 30.5%，仅看提交代码与自报分数的 LLM 评审漏判 6.5%【研究】[112]。厂商文档的措辞因此高度一致：Lovable "自动扫描不能保证完全安全"、Replit "干净的扫描不保证应用安全"、GitHub "你有责任在合并前审查并测试所有输出"、Claude Code 的 Code Review "不批准也不阻止 PR"【官方】[84][87][88][89]。

【推断】对小团队的含义是：验收闭环必须包含智能体无法修改的验证面——隐藏测试、独立复算、人工业务场景走查——而仅凭"智能体自报测试通过"验收的风险在复杂仓库中显著上升。检查点与回滚的共同盲区同样需要注意：由 shell 或 MCP 造成的文件改动、手动编辑、后台子代理编辑（Claude Code、Kiro），以及数据库状态（Lovable 不回滚、Replit 默认不回滚）【官方】[84][88][89][91]。

> 案例 3 Cloudflare workers-oauth-provider：Claude 生成 95% 以上代码、全部 prompt 入库、第三方安全评审（2025 年 3–6 月）
> **背景**：Cloudflare 工程师 Kenton Varda 为 MCP 远程服务器需要一个 OAuth 2.1 Provider 库，几乎全部由 Claude 生成，每个 commit 附上所用 prompt；仓库 HISTORY.md 强调"这不是 vibe coding"——工程师逐行审查并对照 RFC[156]。
> **过程**：读完约 50 个提交的第三方分析显示，初始 prompt 是一段"库该怎么用"的示例代码；约第 20 个提交时工程师首次手动介入（模型无法正确移动类声明）；约第 40 个提交后手动提交明显增多；模型有时顺从工程师提出的错误假设；曾出现用 token 的 SHA-256 作包装密钥材料的缺陷，被人工指出后改为 HMAC[157]。
> **外部评审**：OAuth 安全专家 Neil Madden 发现：公共客户端仍支持 OAuth 2.1 已移除的 implicit grant 且开关未在发 token 处检查；Token ID 随机生成存在偏差（首个提交即存在）；缺少 nosniff/HSTS 等头；测试只覆盖基本功能，缺少对规范 MUST/MUST NOT 与滥用场景的测试。他的总体判断是初版"并不差"但当时不建议使用，并认为"部分错误被工程师发现，部分未被发现"，使用者必须清楚"理想代码长什么样"才能评估 LLM 输出[158]。
> **结果**：库已开源并被 Cloudflare MCP 生态使用，全部 prompt 可在 git 历史中核查[156]。
> **能够支持的判断**："prompt 入库 + 专家逐行审查"是目前可追溯性最好的 AI 生成生产代码实践，但即便如此，第三方评审仍能找出规范遵从与测试不足的问题。独立开发者与小团队难以复制的关键条件是"审阅者具备领域专家级知识"；没有这一条件，同一流程退化为 vibe coding。
> **局限**：单一项目、安全敏感领域、顶级工程师，代表上限而非平均；评审是个人博客而非正式审计。

## 6.5 项目规则、记忆、上下文管理与任务状态维护：长期项目衔接机制

本报告把长期项目衔接拆为三层：**信息保存**（规则文件、记忆、任务记录）、**正确检索**（代码库索引、上下文选择与压缩）、**实际遵循**（模型是否按保存并检索到的信息行动）。图 6-3 概括了三层的供给与证据强度。

**信息保存层供给充分。** 规则文件已经标准化：AGENTS.md 自 2025 年 8 月发布以来被 60,000 多个开源项目采用，2025 年 12 月由 OpenAI 贡献给 Linux Foundation 旗下的 Agentic AI Foundation，Codex、Jules、Gemini CLI、Copilot、Cursor、Devin、Aider、OpenCode 等均支持【官方】[95]；Claude Code 使用 CLAUDE.md 与 .claude/rules（建议 200 行以内），2026 年起也直接读取 AGENTS.md；Cursor 使用 .cursor/rules（建议 500 行以内）并支持可强制的 Team Rules；Codex 合并 AGENTS.md 的默认上限为 32 KiB，超出截断；Lovable 的 Knowledge 为工作区与项目各 10,000 字符并读取仓库中的 AGENTS.md/CLAUDE.md；Replit 由智能体自动创建并更新 replit.md【官方】[84][86][85][89][88]。持久记忆方面，Claude Code 的 Auto memory 由模型自写 MEMORY.md（索引仅加载前 200 行）、Copilot Memory（仓库级事实，28 天未用删除）、Codex Memories（默认关闭）、Qoder CN 的长期记忆（规则优先于记忆）；但 Devin Local 不跨会话持久化记忆、Cursor 的 Memories 管理界面已在 2026 年 1 月移除（功能状态存疑）【官方/观察】[84][87][85][94][90][86]。任务记录方面，Claude Code 的 Task 工具、Kiro 的 tasks.md、Cursor Projects 的跨月上下文提供了显式的任务状态【官方】[84][91][86]。

**检索层依赖上下文窗口与压缩，而两者都有已知衰减。** 代码库检索的趋势是从向量索引回到精确检索加子智能体探索：Cursor 官方文档称已不再存储代码库 embedding 用于搜索，改用本地 Instant Grep 并把宽泛搜索交给独立上下文的 Explore 子智能体；Claude Code 从未依赖向量索引，使用 Grep/Glob/Read 加可选 LSP 插件；Copilot 保留 GitHub 托管的远程语义索引；Devin 用 DeepWiki 自动生成仓库 wiki【官方】[86][84][87][90]。上下文方面，Claude Code 对 1M 窗口模型默认在约 967K 处自动压缩，压缩后重载 CLAUDE.md、记忆与 MCP 工具并重读最近修改的 5 个文件，但路径作用域规则与嵌套 CLAUDE.md 会被一起摘要掉【官方】[84]。研究证据一致指向衰减：Context Rot 研究中 18 个模型在聚焦提示（约 300 token）上的表现显著优于完整提示（约 113K token）【研究】[116]；NoLiMa 中 11/13 模型在 32K 时降到基线一半以下【研究】[117]；多轮对话平均比单轮下降 39%，"走错一步就不再恢复"【研究】[118]。

**遵循层证据最弱，且结论对低基础用户不利。** 两项 2026 年的独立研究均未发现上下文文件能提升任务成功率：Gloaguen 等在 SWE-bench 与含开发者提交的上下文文件的真实 issue 上发现，上下文文件总体未提升成功率，平均推理成本反增 20% 以上——但智能体对文件中的**明确指令**遵循良好，仓库概览类内容无帮助【研究】[119]；Khatri 对 Claude Code 与 Codex 的 288 次运行发现上下文策略对正确性无可测影响【研究】[120]。能提高遵循的是把约束**执行化**：ContextCov 把指令文件约束转为可执行检查，在 SWE-bench Lite 上合规率 88.3%，对比纯提示 67.0%【研究】[121]。厂商自己的表述也印证这一点：Claude Code 文档称规则文件是"上下文而非强制配置"、"过长的 CLAUDE.md 会让 Claude 忽略你真正的指令"，硬性阻止需用 hook；Lovable 文档承认"在很长的对话中指令可能不被一致遵循"；Copilot 文档称其"非确定性，可能不会每次一致"【官方】[84][89][87]。

【推断】三层结论对本报告重点用户的含义是：（1）规则文件应写"必须遵守的具体指令"而非"项目介绍"，而写出一份有效且精简的规则文件本身就是一种技能门槛；（2）真正不可违反的约束应落到 hook、CI 或 lint 等可执行层，而低基础用户通常不具备配置这些机制的能力；（3）记忆与规则的价值主要是减少重复说明，而非提高正确率。换言之，**当前供给在"保存"层解决了用户"记住我说过的话"的表层诉求，但没有解决"按我说过的话行动"的实质诉求**。

## 6.6 产品能力边界与可靠性问题

**长任务成功率**。METR 的时间地平线研究显示，前沿模型能以 50% 概率完成的任务时长自 2019 年起约每 7 个月翻倍（2023 年后约 4.3 个月）；2026 年 2 月 Claude Opus 4.6 的 50% 地平线约 12 小时，但 80% 地平线仅约 1 小时 10 分（二手汇总，原文未能直接核实）【研究】[104]。80% 地平线约为 50% 的五分之一到十分之一，这是"有一半概率独立完成"与"可以放心交付"之间的差距（图 6-4）；Toby Ord 的分析指出智能体成功率随任务时长呈指数衰减，长任务的失败来自子任务链中任一环的失败【研究】[105]。

**基准落差**。SWE-bench Verified 顶分已超 90%，而 SWE-bench Pro 公开集发布时仅 23%、商业私有仓库 10%–18%，失败模式以错误解法与长上下文问题为主【研究】[101]；Terminal-Bench 2.0 的设计目标是让前沿智能体得分低于 65%【研究】[103]。供给侧对大仓库的隐性承认包括：Claude Security 插件建议大仓库分区域扫描、Codex 的 AGENTS.md 32 KiB 截断、Cursor 云端代理不支持多根工作区【官方】[84][85][86]。

**安全漏洞**。Veracode 对 100 多个模型、80 个 CWE 任务的测试显示 45% 的用例引入 OWASP Top 10 漏洞，跨站脚本失败率 86%，且安全表现未随模型迭代改善【研究】[123]；幻觉依赖包研究发现开源模型 21.7%、商用模型至少 5.2% 的推荐包名并不存在，同一幻觉包在重复中 43% 全部重现，构成"slopsquatting"供应链风险【研究】[124]；GitHub Octoverse 2025 指出 vibe coding "可以搭出看似正确却缺少关键鉴权检查的端点"，Broken Access Control 已成为 CodeQL 最常见告警[21]。案例 4 展示了这一问题在一体化平台上的系统性表现。

> 案例 4 Lovable 生成应用的 Supabase RLS 缺失（CVE-2025-48757）与 2026 年两次后续事件
> **背景**：Lovable 自动生成前端并通常接 Supabase 作后端；受影响者为大量用 Lovable 构建并公开部署应用的非专业开发者[151]。
> **事件 1（2025 年 3–5 月）**：Replit 员工 Matt Palmer 发现 Lovable 生成的应用普遍未启用 Supabase 行级安全（RLS），任何人可用公开 anon key 直接读写数据库；扫描发现 170 个项目的 303 个端点存在问题，可读取姓名、邮箱、付款状态与 API 密钥。2025-03-21 报告、04-24 Lovable 2.0 加入"安全扫描"（只检查 RLS 是否存在）、05-29 发布 CVE-2025-48757（CVSS 9.3，CNA 标注争议，Lovable 认为客户对其应用数据负责）[151]。
> **事件 2（2026 年 2 月）**：研究员 Taimur Khan 发现 Lovable "Discover" 页推广的一款教育应用（浏览量超 10 万）缺少 RLS 与基于角色的访问控制，暴露 18,697 条用户记录；Lovable CISO 回应"每个项目发布前都有免费安全扫描，是否采纳建议由用户决定"[152]。
> **事件 3（2026 年 4 月）**：研究员称 Lovable 平台 API 校验 token 但不校验项目所有权，任何免费账户可读取他人项目源码、数据库连接串与 AI 聊天记录（单方说法，未见独立复现）；Lovable 否认发生"数据泄露"，随后承认"意外重新开启了公开项目聊天的访问"[152]。
> **后续**：2026-09 UpGuard 扫描发现 16,326 个 Supabase 数据库存在公开可读表、过半含 PII（不限于 Lovable）；Supabase 称"提供安全默认值与工具，客户控制自己项目的配置"[153]。
> **产品响应**：Lovable 现行的 Quick scan 已在每次发布时自动运行并包含 RLS 检查，Deep scan 检查服务端代码是否尊重所有权规则，可设置"存在 critical 问题时阻止发布"，文档同时声明"未发现问题 ≠ 无风险"【官方】[89]。
> **能够支持的判断**：一体化平台的默认安全姿态把风险转嫁给最不具备判断能力的用户，"扫描提示 + 用户自行决定"模式在 2025–2026 年被反复证明不足；问题不随时间自愈，并扩展到平台自身。生成代码的工具本身也是攻击面。
> **局限**：事件 1 的主要二手来源来自竞争厂商，披露者是 Replit 员工，存在利益关联，但 CVE 与 Lovable 自身承认可交叉印证；事件 3 的影响规模只有研究员单方说法。代表性：高——RLS 缺失是"Supabase + AI 生成应用"的系统性模式而非个案。

**成本不可预测**。主流产品已全面转向按量、按 effort 或按 credit 计费：Claude Code 企业部署平均每开发者每活跃日约 13 美元，长会话、缓存失效、子智能体与 agent teams（约 7 倍）是用量攀升主因【官方】[68]；Replit 的 effort-based 计费把大任务打包为更贵的 checkpoint，Plan 模式不改代码也可能计费【官方】[88]；Lovable 的 Build 按 effort 扣 0.5–2 credit、无事前估价，2026 年 8–10 月连续新增用量预警、工作区限额与"信用耗尽时暂停而非终止"【官方】[75][89]。【推断】2026 年供给侧对"不可预测"的回应是加预算护栏，而不是回到固定价；小团队需要把"每任务成本"纳入验收指标。
